# GitHub 首次发布与在线升级实施方案

日期：2026-11-19。当前基线：本机 Edge 试用候选 1.10.0。本文是开发交接规格，不代表已经创建仓库、发布版本或上线升级。

## 交付范围

| 部分 | 首版做法 |
| --- | --- |
| GitHub | 推送经审查的源码；从固定提交构建 GitHub Release 资产。首发建议 `v1.10.0-rc.1`，标为预发布；服务器默认只检查稳定版。 |
| 自建服务 | Debian 12 原生 systemd 优先。管理员在工作台查看是否有更新、版本说明及升级结果；在服务器执行命令升级。后台自动检查，可缓存上次结果；不自动安装或重启。 |
| Edge 扩展 | 工作台保留 ZIP 下载、版本提示和原目录更新说明；正式浏览器自动更新由后续 Edge Add-ons 发行提供。 |

本地检查时 Git 无提交、未配置远端，大量业务源码未跟踪；先审查首个提交的完整文件清单。复用 `scripts/build_release.py`、`scripts/build_extension.py`、现有加密备份、systemd timers 和反向代理。Windows 4173 保持为日常使用与开发验证环境，Docker、Chrome 和商店发布另列范围。

## 1. 首发与版本来源

1. 先本地准备可审查结果：拟提交文件、排除清单、版本说明、测试结果、归档成员及 SHA-256。源码提交与服务器发布包分别使用明确的收录规则；不要整目录盲加。排除 `.local`、真实 `.env`、数据库及附件、媒体、备份、浏览器配置、真实 QA 截图、私有主机与运维资料、密钥及令牌。注意现有 `.gitignore` 特意放行 `extension/dist/*.zip`，旧 ZIP 不应混入源码历史；打包脚本递归纳入 `docs/` 和 `extension/`，需要单独收紧。验证嵌套 ZIP 内容也无私有文件；需要发布的内部说明先改用示例或移出发布范围。
2. GitHub 所有者、仓库名和可见性以用户指定为准；未指定或未授权时，将本地审查与草稿素材准备好，再确认具体目的地。建议先私有；公开前核对源码与文档、第三方许可及授权。不要把已有服务地址当成 GitHub 配置。私有仓库使用最小权限的只读下载凭据，凭据仅留在服务器；不传给网页、扩展、日志和其他下载域。
3. 首个 Release 从干净 checkout 的明确提交构建：前端依赖锁和构建、扩展测试与打包、Django 测试和迁移漂移检查、发布脚本测试。生成版本化服务包 `website-workspace-v1.10.0-rc.1.tar.gz`、匹配的扩展 ZIP、`release-manifest.json` 及其签名、校验文件。服务包应内含同一次构建的同字节扩展 ZIP，前端产物预构建；GitHub 自带的源码归档不能作为部署包。RC 的服务端标识可带后缀，扩展 `manifest.version` 仍使用浏览器支持的数字格式；同一扩展版本的 ZIP 不允许后来变内容，改了就升版本。
4. 清单最低字段：格式版本、项目标识、发行轨道、版本及 tag、提交 SHA、资产名称/大小/SHA-256、最低可直升版本、目标平台、扩展版本与 API 兼容范围。版本、tag、资产与发布说明都从同一候选构建生成。CI 平时只读；发布作业最小权限，草稿上传、审查通过后再发布；同一 tag 或资产不可被覆盖，可用时开启 GitHub immutable releases。升级入口接受部署时固定的项目仓库和独立安装的发布公钥，校验签名、清单、资产哈希与大小；不能从待安装包接受新信任公钥，私钥不放仓库或运行主机。首版可人工离线签名固定清单，避免为自动签名搭一套新服务。

## 2. 自建服务升级

**发现更新。** 服务器按固定仓库、轨道和 SemVer 查找新版，区分预发布、无更新、上游暂不可用；默认稳定轨道排除草稿和 RC，选择 RC 要显式开启。管理员页面只读展示当前/目标版本、检查时间、发布说明、命令和最近升级状态。检查带超时和缓存；GitHub 不可用不影响登录、收藏或同步。浏览器不直连 GitHub，也不提供 Web shell、用户自填仓库或任意下载地址。更新命令支持预检和指定明确版本；预检不动线上数据或服务。

**布局。** 建议 `/opt/website-workspace/releases/<version>/` 存各版代码、独立 venv 与构建产物，`current` 原子指向运行版本；原环境文件、`DATA_DIR`、数据库、媒体、密钥、域名/代理设置继续独立。逐一核对现有 systemd、timer、静态资源路径和反向代理；为旧版直接解包到 `/opt/website-workspace` 的部署提供一次性迁移步骤。真实 Nginx 和通用 Caddy 模板要区分；升级不顺带切换代理。权限受控的本机运维工具负责升级，Web 进程不能写程序目录或提升权限。

**执行顺序。** ① 拿维护锁并记录当前版本、配置定位和原定时器状态；在线时下载、验签、安全解包（拒绝路径逃逸、链接、特殊或重复成员并限制展开大小）、安装锁定的二进制依赖并做预检。② 开启维护入口，线上写请求返回可重试的 `503`，不伪装成认证失败；暂停并排空图标、清理和备份任务，停止 Web 写入后创建并实际试恢复当前数据库与媒体的加密备份，检查截图与图标文件均可恢复。③ 在维护窗口内用现有配置、应用用户运行迁移并切换 `current`；保持外部写入关闭，检查版本、静态资源、迁移、健康页，抽查登录、收藏读取、截图和图标，必要时仅在隔离数据中做写入冒烟。④ 检查通过后恢复入口及原来启用的定时器，确认补图调度实际运行，不需人工敲 `runjobs`。保留上一版本及已验证备份。按 700MB 级低内存目标测量，服务器不跑 Node 构建，不新增常驻队列服务。

**失败与回退。** 下载、验签、预检失败：旧服务继续；迁移前失败：恢复原服务及定时器状态；迁移开始后或新版健康检查失败：保持维护状态，保存失败现场，从同一次备份成对恢复数据库与媒体，切回旧版程序与 venv，验证后再开放。用持久化状态记录阶段，进程中断后能辨别是否已迁移或切换；禁止盲目重跑。重新对外开放后如已产生新写入，不自动恢复旧备份；管理员先保全新数据，再决定前滚修复或停机恢复。升级不轮换密钥、不重置账号或配对，也不清理浏览器 Outbox。

## 3. 扩展更新

现有 ZIP 安装：工作台提示新版本并提供经服务端发布验证的包。使用者备份旧扩展目录，在原路径更新文件并在原扩展条目重新加载；不先卸载。升级测试用带待同步截图的实际队列，核对同一扩展 ID、账号、配对、备注和最终同步。保留旧扩展与新服务的过渡兼容；不因弹出升级提示阻止旧扩展收藏。正式 Edge Add-ons 的安装、自动更新及可能涉及的扩展 ID/本地存储迁移单独验收，不声称站内 ZIP 能静默更新。不要通过运行远程代码或修改浏览器策略来实现替代更新。

## 4. 最小验收与发布门槛

- GitHub 候选版：干净 checkout 可构建；清单和签名校验通过；ZIP 与实际站内下载一致；确认无真实数据、私有配置或凭据；记录仓库、tag、提交、资产与 SHA-256。
- 隔离 Debian：新装一次；使用有真实结构的合成数据从现有版升级一次，涵盖账号、分类、备注、配对、截图及图标。模拟包损坏、迁移/启动失败及升级进程中断，证明旧版保全、状态可恢复；校验维护时扩展离线排队、服务恢复后自动续传且不重复。
- 用日常启动方式验收图标定时任务：真实 Edge 在当前网页弹窗收藏、关闭弹窗，清楚记录图标任务及终态；不手动运行 `runjobs` 补证据。验证 `www.qianwen.com` 的原始入口与跳转；在可访问的环境测 ChatGPT。第二账号隔离继续在测试配置验证，避免动日常 4173 配对。报告峰值内存、磁盘、停机时间及未测项。
- 上述本机/隔离证据和版本差异整理成可审核交付。只在已确认的 GitHub 目标和授权范围发布；正式稳定版及生产升级须以真实演练结果为准。Github Release 不等于部署生产，预发布不推给稳定轨道。
